## 1. Background: Why NUMA Matters

### Uniform vs. Non-Uniform Memory Access

On single-socket machines, all memory accesses have uniform latency (**UMA**). On
multi-socket servers, each CPU socket has its own directly-attached RAM, forming
a **NUMA node**:

```
┌──────────────────┐              ┌──────────────────┐
│   Socket 0       │              │   Socket 1       │
│  CPU cores 0-15  │              │  CPU cores 16-31 │
│       ↕          │  ~1.7× cost  │       ↕          │
│  Local RAM 64GB  │◄────────────►│  Local RAM 64GB  │
│  (NUMA node 0)   │  inter-      │  (NUMA node 1)   │
└──────────────────┘  connect     └──────────────────┘
```

- **Local access** (core → same-node RAM): ~80 ns
- **Remote access** (core → other-node RAM): ~140 ns

Without explicit control, the OS may place memory and threads on different nodes,
causing all accesses to traverse the interconnect — a **~40% latency penalty**.

### What This Runtime Controls

| Concern | Without this runtime | With this runtime |
|---------|----------------------|-------------------|
| Memory placement | OS decides (first-touch policy) | Explicit per-node allocation |
| Thread scheduling | OS may migrate across sockets | Pinned to a NUMA node's cores |
| Cross-node sync | Generic locks (cache-line bouncing) | Lightweight futex-based signaling |

## 3. Platform Abstraction & Build Configuration

### Three-Tier Fallback Strategy

The code uses nested `#ifdef` guards to implement graceful degradation:

```
#ifdef __linux__                    ← Tier 2: Linux without libnuma
  #ifdef TRITON_HAS_NUMA           ← Tier 1: Linux with libnuma (best)
    numa_alloc_onnode(...)
  #endif
  mmap + mbind fallback
#else                               ← Tier 3: Non-Linux (malloc)
  std::malloc(...)
#endif
```

| Tier | Condition | Memory | Pinning | Signaling |
|------|-----------|--------|---------|-----------|
| 1 | `__linux__` + `TRITON_HAS_NUMA` | `numa_alloc_onnode` | `numa_sched_setaffinity` | futex |
| 2 | `__linux__` only | `mmap` + sysfs parse | no-op | futex |
| 3 | Other OS | `malloc` | no-op | `std::this_thread::yield` spin |

### Symbol Visibility

```cpp
#if defined(__GNUC__)
#define EXPORT __attribute__((visibility("default")))
#elif defined(_MSC_VER)
#define EXPORT __declspec(dllexport)
#endif
```

Modern compilers default to hidden symbol visibility (`-fvisibility=hidden`).
The `EXPORT` macro explicitly marks each runtime function as visible in the
shared library's dynamic symbol table, enabling:

- **LLVM JIT**: `dlsym()` resolution at runtime
- **Python ctypes**: `ctypes.CDLL(path).triton_get_numa_id`
- **Direct linking**: standard linker symbol resolution

### Build System Integration

The `TRITON_HAS_NUMA` macro is set by CMake when `libnuma` is detected:

```cmake
find_library(NUMA_LIB numa)
if(NUMA_LIB)
  target_compile_definitions(TritonCPURuntime PRIVATE TRITON_HAS_NUMA)
  target_link_libraries(TritonCPURuntime PRIVATE ${NUMA_LIB})
endif()
```

## 4. API Reference

All functions use C linkage (`extern "C"`) and are safe to call from any language.

### `triton_get_numa_id`

```cpp
EXPORT int32_t triton_get_numa_id();
```

Returns the NUMA node ID of the CPU core the calling thread is currently
executing on.

**Implementation path**:
1. `sched_getcpu()` → get current CPU core number
2. If libnuma: `numa_node_of_cpu(cpu)` → NUMA node
3. Fallback: parse `/sys/devices/system/cpu/cpu<N>/topology/physical_package_id`
4. Ultimate fallback: return `0`

---

### `triton_numa_alloc`

```cpp
EXPORT void *triton_numa_alloc(int64_t size_bytes, int32_t numa_node);
```

Allocates `size_bytes` of memory bound to the physical RAM of `numa_node`.

**Implementation path**:
1. If libnuma: `numa_alloc_onnode(size, node)` — single-call allocation + binding
2. Linux fallback: `mmap(MAP_PRIVATE | MAP_ANONYMOUS)` + `mbind(MPOL_BIND)`
3. Non-Linux: `std::malloc(size)` (no NUMA guarantee)

**Returns**: Pointer to allocated memory, or `nullptr` on failure.

> [!IMPORTANT]
> The returned pointer **must** be freed with `triton_numa_free()`, not `free()`.
> Mismatched free methods cause undefined behavior because `numa_alloc` and
> `mmap` use different kernel bookkeeping than `malloc`.

---

### `triton_numa_free`

```cpp
EXPORT void triton_numa_free(void *ptr, int64_t size_bytes);
```

Frees memory allocated by `triton_numa_alloc`. The `size_bytes` parameter is
required because both `numa_free()` and `munmap()` need the original allocation
size (unlike `free()`, the kernel does not track it for these allocation methods).

---

### `triton_numa_pin_thread`

```cpp
EXPORT void triton_numa_pin_thread(int32_t numa_node);
```

Restricts the calling thread to CPU cores belonging to `numa_node`. After this
call, the OS scheduler will never migrate this thread to a different node's
cores.

**Implementation**: Queries `numa_node_to_cpus()` for the core bitmask, then
calls `numa_sched_setaffinity(0, mask)` (where `0` = current thread).

**Fallback**: No-op on systems without libnuma.

---

### `triton_numa_wait`

```cpp
EXPORT void triton_numa_wait(int32_t signal_id);
```

Blocks the calling thread until `signal_id` is set to non-zero by a
corresponding `triton_numa_notify()` call. Resets the signal to `0` after waking
(single-use per wait cycle).

**Valid range**: `signal_id ∈ [0, 1024)`

---

### `triton_numa_notify`

```cpp
EXPORT void triton_numa_notify(int32_t signal_id, int32_t numa_dst);
```

Signals a waiting thread by setting `signal_id` to `1` and waking any thread
blocked in `triton_numa_wait(signal_id)`.

The `numa_dst` parameter is reserved for future NUMA-local signal table
optimizations and is currently unused.

## 5. Concurrency Model & Edge Cases

### 5.1 Signal Table Design

The signal table is a global array of 1024 `std::atomic<int32_t>` values:

```cpp
struct SignalTable {
  std::atomic<int32_t> signals[MAX_SIGNALS]; // each is 0 or 1
};
static SignalTable g_signal_table;           // process-wide singleton
```

**Design trade-offs**:

- **Fixed-size array** (vs. dynamic map): Zero allocation overhead, cache-friendly
  for known signal ID ranges, no locks needed for lookup. The downside is a hard
  cap at 1024 concurrent signals.
- **Global instance**: All NUMA nodes share one table. This means the cache line
  holding a signal may bounce between sockets during wait/notify. A future
  optimization could use per-node tables to keep signaling traffic local.

### 5.2 The Spin-Then-Sleep Wait Strategy

```cpp
// Phase 1: spin (user-space, ~1µs)
for (int spin = 0; spin < 1024; ++spin) {
    if (signal.load(std::memory_order_acquire) != 0) {
        signal.store(0, std::memory_order_release);
        return;  // fast path
    }
    __builtin_ia32_pause();
}

// Phase 2: futex sleep (kernel-space, 0 CPU while sleeping)
while (signal.load(std::memory_order_acquire) == 0) {
    futex_wait(&signal, 0);
}
signal.store(0, std::memory_order_release);
```

**Rationale**: A kernel transition (`syscall`) costs ~1–5 µs. For signals that
arrive within microseconds (common in tiled computation), the spin loop catches
them with zero kernel overhead. If the signal takes longer, the futex avoids
wasting CPU cycles.

**`__builtin_ia32_pause()`**: The x86 `PAUSE` instruction serves two purposes:
1. Hints to the CPU that this is a spin loop → reduces power consumption
2. Prevents memory-order violation penalties in the CPU pipeline on spin-loop exit

### 5.3 Race Condition: Lost Wake-Up (Prevented)

The most critical concurrency bug in wait/notify systems is the **lost wake-up**:

```
Thread B (waiter)                    Thread A (notifier)
────────────────                    ────────────────────
reads signal → 0
                                    signal.store(1)
                                    futex_wake(&signal)  ← wakes nobody!
futex_wait(&signal, expected=0)
  → kernel sees *signal == 1, not 0
  → returns immediately ✓
```

**How it's prevented**: The `futex_wait` syscall performs an **atomic
compare-and-block**: the kernel checks `*addr == expected` and suspends the
thread as a single indivisible operation. If the value has already changed to `1`
by the time the kernel examines it, `futex_wait` returns immediately instead of
sleeping. This eliminates any window where a wake-up can be lost between checking
the value and sleeping.

### 5.4 Race Condition: Spurious Wake-Up (Handled)

Futex can wake a thread even when the value hasn't changed (e.g., due to signal
delivery or kernel implementation details). The code handles this with a
**`while` loop**:

```cpp
while (signal.load(std::memory_order_acquire) == 0) {
    futex_wait(&signal, 0);  // may return spuriously
}
// Only exits when signal is genuinely non-zero
```

Each iteration re-checks the signal and re-sleeps if it was a spurious wake.

### 5.5 Memory Ordering Guarantees

The runtime uses **acquire-release semantics** to establish a happens-before
relationship between producer and consumer:

```
Producer (Thread A)                  Consumer (Thread B)
───────────────────                  ────────────────────
write data to buffer
signal.store(1, release) ──┐
                           │ happens-before
                           └──► signal.load(acquire)
                                read data from buffer ← sees A's writes ✓
```

| Operation | Ordering | Guarantee |
|-----------|----------|-----------|
| `signal.load(acquire)` | `memory_order_acquire` | All writes from the thread that did the matching `release` store are visible |
| `signal.store(1, release)` | `memory_order_release` | All preceding writes by this thread are visible to the acquiring reader |
| `signal.store(0, relaxed)` (constructor) | `memory_order_relaxed` | No ordering guarantees (safe because no concurrent access during init) |

> [!CAUTION]
> Using `memory_order_relaxed` for the signal store in `triton_numa_notify`
> would break correctness: the consumer thread could see `signal == 1` but still
> read stale data from the buffer because the compiler and CPU are free to
> reorder the buffer writes after the signal store.

### 5.6 Signal Reuse Safety

After waking, the consumer **resets the signal to `0`**:

```cpp
signal.store(0, std::memory_order_release);
```

This allows the same `signal_id` to be reused for the next synchronization
round. However, the current design assumes **1:1 signaling** (one producer, one
consumer per signal ID per round). Using the same signal ID for multiple
concurrent producers or consumers without external coordination can cause:

- **Multiple producers**: Second store of `1` is idempotent, but only one
  `futex_wake(1)` is issued per notify — if two consumers are waiting, one may
  remain asleep.
- **Multiple consumers**: Only one thread will see the `1` and reset it; others
  may spin or sleep indefinitely.

> [!WARNING]
> Each `signal_id` should be used by exactly one producer-consumer pair per
> synchronization round. If fan-out is needed, use separate signal IDs.

### 5.7 Memory Allocation Thread Safety

- **`numa_alloc_onnode`**: Thread-safe (libnuma is internally synchronized).
- **`mmap`/`munmap`**: Thread-safe (kernel serializes VMA operations).
- **`malloc`/`free`**: Thread-safe (glibc uses per-thread arenas).

No additional locking is needed in the allocation/free functions.

### 5.8 `mbind` Failure Resilience

```cpp
long rv = mbind(ptr, size, MPOL_BIND, &nodemask, ...);
if (rv != 0) {
    fprintf(stderr, "triton_numa_alloc: mbind to node %d failed\n", numa_node);
}
return ptr; // memory is still usable, just possibly on the wrong node
```

`mbind` can fail if:
- The node doesn't have enough free memory
- The kernel doesn't support the requested policy
- The process lacks `CAP_SYS_NICE` for strict binding

The code treats this as a **soft failure**: the memory is still valid and usable,
but may not reside on the requested node. Performance degrades, but correctness
is preserved.

### 5.9 Wait/Notify: Application-Level Only (No libnuma or Pagetable Interaction)

The `triton_numa_wait` / `triton_numa_notify` signaling mechanism is **entirely
application-level** for coordination. It does **not** interact with libnuma or
OS-level pagetable / NUMA memory policy.

| Concern | Wait/Notify | NUMA Allocation (separate) |
|---------|-------------|----------------------------|
| **libnuma** | No — zero calls | Yes — `numa_alloc_onnode`, `mbind`, etc. |
| **Pagetables** | No — no `mbind`, `migrate_pages`, or NUMA policy | Yes — pages bound to NUMA nodes |
| **Signal table** | Process BSS (loader-allocated) | N/A |
| **Kernel involvement** | Standard futex only (scheduler block/wake) | `mmap`, `mbind` for allocation |

**Implementation summary**:

- The signal table (`g_signal_table`) is a `static` global — ordinary process
  memory in BSS, allocated by the loader. No `triton_numa_alloc` or NUMA-aware
  allocation.
- Wait/notify use `std::atomic<int32_t>` for signals and Linux `futex` syscalls
  for blocking/waking. The kernel's futex subsystem handles scheduling only;
  it does not manipulate pagetables or NUMA policy.
- The `numa_dst` parameter to `triton_numa_notify` is reserved for future use
  and is currently unused.

The **data** that producer and consumer coordinate over (via `tl.numa_store` /
`tl.numa_load`) may live in NUMA-allocated buffers. The wait/notify primitives
only coordinate *when* that data is ready — they do not touch libnuma or
pagetables.
